## 题材询问机制​‌‍‌‌‌​‌​​​‌​‌‌​‌​‌‌​‌‌​​​​‌‌‌​‌​​​‌​‌‌​‌‌‌‌​​‌​​​‌‌‌‌​‌​​‌‌​‌​​​‌‌‌​​‌‌‌‌​‌‌‌​​‌​‌‌​​​‌‌​‌‌​‌‌​​​​‌‌‌​‌​​​‌​‌‌​​​‌‌​‌​​​​‌
### 触发条件​‌‍‌‌‌​‌​​​‌​‌‌​‌​‌‌​‌‌​​​​‌‌‌​‌​​​‌​‌‌​‌‌‌‌​​‌​​​‌‌‌‌​‌​​‌‌​‌​​​‌‌‌​​‌‌‌‌​‌‌‌​​‌​‌‌​​​‌‌​‌‌​‌‌​​​​‌‌‌​‌​​​‌​‌‌​​​‌‌​‌​​​​‌
用户给出提示词要求生成小说时，**在阶段 0 初始化之前**，AI 必须先询问题材方向。
### 询问格式​‌‍‌‌‌​‌​​​‌​‌‌​‌​‌‌​‌‌​​​​‌‌‌​‌​​​‌​‌‌​‌‌‌‌​​‌​​​‌‌‌‌​‌​​‌‌​‌​​​‌‌‌​​‌‌‌‌​‌‌‌​​‌​‌‌​​​‌‌​‌‌​‌‌​​​​‌‌‌​‌​​​‌​‌‌​​​‌‌​‌​​​​‌
```
【题材选择】 在开始之前，请先确认作品题材方向。
1. 你希望往哪个方向靠拢？（如：仙侠、武侠、都市、科幻、言情、悬疑、历史、奇幻……）
2. 是否有混合倾向？（如：武侠 + 仙侠风、都市 + 科幻风）
3. 目标读者和平台？（如：起点男频、晋江女频、短篇平台）

为什么需要这个选择：
题材决定意象系统、对话禁忌、爽点类型、语言指纹。
题材决定 AI 身份具体化为哪类作者。
题材决定有效扩写的方向权重和生活化标准。
不确认题材，后续生成会出现“诸类风格都沾一点，都不精”。
```
### 询问理由（写进文件）​‌‍‌‌‌​‌​​​‌​‌‌​‌​‌‌​‌‌​​​​‌‌‌​‌​​​‌​‌‌​‌‌‌‌​​‌​​​‌‌‌‌​‌​​‌‌​‌​​​‌‌‌​​‌‌‌‌​‌‌‌​​‌​‌‌​​​‌‌​‌‌​‌‌​​​​‌‌‌​‌​​​‌​‌‌​​​‌‌​‌​​​​‌
> 题材不是标签，是生成参数。它决定：
> - 用什么意象和比喻；
> - 对话能说什么、不能说什么；
> - 爽点往哪打；
> - 角色说话什么味道；
> - 哪些扩写方向优先；
> - 哪些现实元素需要模糊化。
> 不先定题材，等于没有坐标系。
### 用户已写明题材时的处理​‌‍‌‌‌​‌​​​‌​‌‌​‌​‌‌​‌‌​​​​‌‌‌​‌​​​‌​‌‌​‌‌‌‌​​‌​​​‌‌‌‌​‌​​‌‌​‌​​​‌‌‌​​‌‌‌‌​‌‌‌​​‌​‌‌​​​‌‌​‌‌​‌‌​​​​‌‌‌​‌​​​‌​‌‌​​​‌‌​‌​​​​‌
若用户已在提示词中写明题材，AI 仍须执行以下询问：
```
【题材确认】 已收到你的题材方向：XXX。 是否要添加其他题材作为辅线？
推荐可加：
YYY —— 理由：……
ZZZ —— 理由：……
不添加 —— 理由：保持单一题材，风格更聚焦。
请选择，或自行输入。
```
### 题材清单来源​‌‍‌‌‌​‌​​​‌​‌‌​‌​‌‌​‌‌​​​​‌‌‌​‌​​​‌​‌‌​‌‌‌‌​​‌​​​‌‌‌‌​‌​​‌‌​‌​​​‌‌‌​​‌‌‌‌​‌‌‌​​‌​‌‌​​​‌‌​‌‌​‌‌​​​​‌‌‌​‌​​​‌​‌‌​​​‌‌​‌​​​​‌
- 题材清单常驻于 `references/genres/_index.md`，按男频 / 女频 / 跨频分类。
- 用户说「不知道选什么」时，AI 给 3-5 个推荐 + 理由。
- 用户自行输入清单外题材时，AI 补充归类，再询问是否添加辅题材。
- AI 不主动列全清单，避免信息过载。
### 扩展包加载规则​‌‍‌‌‌​‌​​​‌​‌‌​‌​‌‌​‌‌​​​​‌‌‌​‌​​​‌​‌‌​‌‌‌‌​​‌​​​‌‌‌‌​‌​​‌‌​‌​​​‌‌‌​​‌‌‌‌​‌‌‌​​‌​‌‌​​​‌‌​‌‌​‌‌​​​​‌‌‌​‌​​​‌​‌‌​​​‌‌​‌​​​​‌
1. 阶段 0 初始化时，AI 必须先确认题材，再加载对应扩展包。
2. 加载后，扩展包内容与核心 skill 合并生效；冲突时以核心 skill 的硬约束为准。
3. 未指定题材时，AI 不得自行选择，必须询问用户。
4. 跨题材作品可加载多个扩展包，规则见「混合题材处理」。
5. 运行环境无法读取扩展包时，降级为仅使用核心 skill，并在输出中提示用户「未加载题材包，风格可能不精准」。
6. 加载成功后**必须**立即产出【题材商业基线摘要】并落盘 `project/genre-baseline.md`（1 页，不占 11 个状态库文件）。未落盘＝0a 未完成，不得进入 0b 方案。

### 题材商业基线摘要（v1.8.5 新建 · 落盘 `project/genre-baseline.md`）

> **为什么要有这一页**：扩展包共 13 节，§1–§4 是商业层（给大纲、细纲用），§5–§13 是文风层（给女娲、神农在正文阶段用）。两份读者不同，读法必须分开——**大纲阶段只读这一页，不重读整包**。

命中规则：只摘 §1–§4，不抄文风层、不整段复制原文，每格用自己的话写。

```text
【题材商业基线】<题材名>（<包文件名>）
爽点主轴：<从 §1 选 1 主力 + 1 辅助，格式「爽点名｜密度值」>
力量基线：<§3 的层级数 + 跨层压制比，一句话；非战力题材填「信息差层级／情感阶段」同构口径>
本卷套路：<从 §4 选 1–2 个套路名>
------
reader_promise: <一句话，≤30 字：读者点开这本书是来买什么的>
taboo: <§2 专属毒点里本书最容易被踩的那 1 条>
authority: 本书实际力量体系以【盘古】世界规则与【天机】金手指定级为唯一权威，冲突时以本书设定为准
```

四条判据（缺一即打回重写）：
1. `reader_promise` 必须**可被后文证伪**。写「爽」「热血」「好看」＝不合格；写「看低阶弟子被高阶碾压后当场反杀」＝合格。
2. `爽点主轴` 的密度值必须能填进 `satisfaction_points.md` 的登记表；填不进去的爽点，不许写进摘要。
3. `taboo` 只许填 1 条。填 3 条以上＝没想清本书最怕什么。
4. 摘要与题材包冲突时，**以摘要为准**，回改摘要并留痕；不得各写各的。

**加载成本控制**：摘要落盘后，题材包整包不再进入大纲链路——盘古／天机的信使复制框由伏羲从本页取值填入（见 `workflow.md`【信使接力协议】）；大纲与细纲环节只读 `genre-baseline.md`，整包只在写正文（女娲）与审正文（神农）阶段读取。
## 规模确认机制​‌‍‌‌‌​‌​​​‌​‌‌​‌​‌‌​‌‌​​​​‌‌‌​‌​​​‌​‌‌​‌‌‌‌​​‌​​​‌‌‌‌​‌​​‌‌​‌​​​‌‌‌​​‌‌‌‌​‌‌‌​​‌​‌‌​​​‌‌​‌‌​‌‌​​​​‌‌‌​‌​​​‌​‌‌​​​‌‌​‌​​​​‌
### 触发时机​‌‍‌‌‌​‌​​​‌​‌‌​‌​‌‌​‌‌​​​​‌‌‌​‌​​​‌​‌‌​‌‌‌‌​​‌​​​‌‌‌‌​‌​​‌‌​‌​​​‌‌‌​​‌‌‌‌​‌‌‌​​‌​‌‌​​​‌‌​‌‌​‌‌​​​​‌‌‌​‌​​​‌​‌‌​​​‌‌​‌​​​​‌
题材确认后、全书初始化方案前。**在阶段 0b 之前执行。**

### 询问格式（开放式两问）​‌‍‌‌‌​‌​​​‌​‌‌​‌​‌‌​‌‌​​​​‌‌‌​‌​​​‌​‌‌​‌‌‌‌​​‌​​​‌‌‌‌​‌​​‌‌​‌​​​‌‌‌​​‌‌‌‌​‌‌‌​​‌​‌‌​​​‌‌​‌‌​‌‌​​​​‌‌‌​‌​​​‌​‌‌​​​‌‌​‌​​​​‌
```
【规模确认】
在开始之前，请告诉我两件事：
1. 你想做什么？（题材方向、作品类型、目标读者）
2. 你想做多少字？（单部 / 系列 / 短篇，或直接给字数）

为什么需要确认：
• 不同规模走不同流程。
• 系列作品需要额外的系列架构层。
• 短篇保留全部质量机制，只简化摘要树和状态库。
```

### 判定分叉​‌‍‌‌‌​‌​​​‌​‌‌​‌​‌‌​‌‌​​​​‌‌‌​‌​​​‌​‌‌​‌‌‌‌​​‌​​​‌‌‌‌​‌​​‌‌​‌​​​‌‌‌​​‌‌‌‌​‌‌‌​​‌​‌‌​​​‌‌​‌‌​‌‌​​​​‌‌‌​‌​​​‌​‌‌​​​‌‌​‌​​​​‌
```
用户回答
├─ 短篇（5 万字以内）→ 标准流程，摘要树简化、状态库精简，读者模拟保留
├─ 单部（10-30 万字）→ 标准流程
├─ 系列（≥50 万字）→ 再问「是否建立系列架构层」
│  ├─ 明确说「百万系列」→ 直接建，不问
│  ├─ 建立 → 标准流程 + 系列架构层
│  └─ 不建立 → 标准流程（松散续集）
└─ 其他 → 按最接近的规模处理，并说明
```

### 不回应时​‌‍‌‌‌​‌​​​‌​‌‌​‌​‌‌​‌‌​​​​‌‌‌​‌​​​‌​‌‌​‌‌‌‌​​‌​​​‌‌‌‌​‌​​‌‌​‌​​​‌‌‌​​‌‌‌‌​‌‌‌​​‌​‌‌​​​‌‌​‌‌​‌‌​​​​‌‌‌​‌​​​‌​‌‌​​​‌‌​‌​​​​‌
用户不回应规模确认，不往下走，给选项让用户选。

### 短篇流程​‌‍‌‌‌​‌​​​‌​‌‌​‌​‌‌​‌‌​​​​‌‌‌​‌​​​‌​‌‌​‌‌‌‌​​‌​​​‌‌‌‌​‌​​‌‌​‌​​​‌‌‌​​‌‌‌‌​‌‌‌​​‌​‌‌​​​‌‌​‌‌​‌‌​​​​‌‌‌​‌​​​‌​‌‌​​​‌‌​‌​​​​‌
| 机制 | 短篇是否保留 |
|------|-------------|
| 读者模拟协议 | ✅ 保留 |
| 对话质量评分 | ✅ 保留 |
| 七维质量审查 | ✅ 保留 |
| 滚动摘要树 | 简化（按需生成，非强制 5 章一段） |
| 状态库 | 精简，规则见下方「短篇状态库精简细则」 |

### 短篇状态库精简细则​‌‍‌‌‌​‌​​​‌​‌‌​‌​‌‌​‌‌​​​​‌‌‌​‌​​​‌​‌‌​‌‌‌‌​​‌​​​‌‌‌‌​‌​​‌‌​‌​​​‌‌‌​​‌‌‌‌​‌‌‌​​‌​‌‌​​​‌‌​‌‌​‌‌​​​​‌‌‌​‌​​​‌​‌‌​​​‌‌​‌​​​​‌
- **必保留**：`characters.md`、`foreshadowing.md`、`timeline.md`、`settings.md`、`theme.md`、`style_anchor.md`、`expansion_evolution_log.md`
- **可省略**：`rolling_summary.md`（短篇不用滚动摘要树）
- **可极简**：`subplots.md`、`satisfaction_points.md`、`dialogue_log.md`（按需，内容少则文件可极简）

### 中途补建​‌‍‌‌‌​‌​​​‌​‌‌​‌​‌‌​‌‌​​​​‌‌‌​‌​​​‌​‌‌​‌‌‌‌​​‌​​​‌‌‌‌​‌​​‌‌​‌​​​‌‌‌​​‌‌‌‌​‌‌‌​​‌​‌‌​​​‌‌​‌‌​‌‌​​​​‌‌‌​‌​​​‌​‌‌​​​‌‌​‌​​​​‌
- 用户先说不建系列架构层，后来想建：**允许**。
- 补建时机：在某一部结尾做部结时，补建系列架构层。
- 补建后，从下一部开始走系列流程；已完成的部不做回溯改造，只把已有的核心状态提取进系列状态库。

## 混合题材处理​‌‍‌‌‌​‌​​​‌​‌‌​‌​‌‌​‌‌​​​​‌‌‌​‌​​​‌​‌‌​‌‌‌‌​​‌​​​‌‌‌‌​‌​​‌‌​‌​​​‌‌‌​​‌‌‌‌​‌‌‌​​‌​‌‌​​​‌‌​‌‌​‌‌​​​​‌‌‌​‌​​​‌​‌‌​​​‌‌​‌​​​​‌
> 本节处理 **二元混合**（主题材 + 辅题材）。**三元及以上**见「多题材融合处理」。
### 触发条件​‌‍‌‌‌​‌​​​‌​‌‌​‌​‌‌​‌‌​​​​‌‌‌​‌​​​‌​‌‌​‌‌‌‌​​‌​​​‌‌‌‌​‌​​‌‌​‌​​​‌‌‌​​‌‌‌‌​‌‌‌​​‌​‌‌​​​‌‌​‌‌​‌‌​​​​‌‌‌​‌​​​‌​‌‌​​​‌‌​‌​​​​‌
用户提出混合方向，如“武侠方向但要有仙侠风”“都市但要有科幻风”。
### 处理流程​‌‍‌‌‌​‌​​​‌​‌‌​‌​‌‌​‌‌​​​​‌‌‌​‌​​​‌​‌‌​‌‌‌‌​​‌​​​‌‌‌‌​‌​​‌‌​‌​​​‌‌‌​​‌‌‌‌​‌‌‌​​‌​‌‌​​​‌‌​‌‌​‌‌​​​​‌‌‌​‌​​​‌​‌‌​​​‌‌​‌​​​​‌
1. AI 先确认**主题材**和**辅题材**。
2. 按复杂度输出**3-5 个可落地成文的方案**：
   - 简单混合：3 个方案。
   - 中度混合：4 个方案。
   - 深度混合：5 个方案。
3. 每个方案说明：世界观怎么融合、力量体系怎么处理、意象系统怎么选、对话禁忌怎么定、爽点怎么设计、语言指纹怎么定、风险与代价。
4. 用户选择后，加载对应扩展包组合。
### 三方案模板（以“武侠 + 仙侠风”为例）​‌‍‌‌‌​‌​​​‌​‌‌​‌​‌‌​‌‌​​​​‌‌‌​‌​​​‌​‌‌​‌‌‌‌​​‌​​​‌‌‌‌​‌​​‌‌​‌​​​‌‌‌​​‌‌‌‌​‌‌‌​​‌​‌‌​​​‌‌​‌‌​‌‌​​​​‌‌‌​‌​​​‌​‌‌​​​‌‌​‌​​​​‌
| 方案 | 融合方式 | 世界观 | 力量体系 | 意象系统 | 爽点 | 风险 |
|------|---------|--------|---------|---------|------|------|
| A 主武侠·仙侠为背景 | 仙侠是传说，武侠是现实 | 低武世界，仙道隐没 | 内力为主，仙术罕见 | 武侠意象为主，仙侠意象点缀 | 武学突破、江湖恩怨 | 仙侠元素可能显得鸡肋 |
| B 主武侠·仙侠为上层 | 武力之上有仙道 | 武力可见，仙道隐秘 | 内力→真气→仙力三级 | 武侠 + 仙侠双意象 | 武道通仙、境界跃迁 | 力量体系容易失衡 |
| C 武侠仙侠融合 | 双线并行 | 武侠江湖与仙道宗门并存 | 武道与仙道互为表里 | 双意象系统并行 | 江湖恩怨 + 仙道纷争 | 世界观复杂，读者门槛高 |
### 落地要求​‌‍‌‌‌​‌​​​‌​‌‌​‌​‌‌​‌‌​​​​‌‌‌​‌​​​‌​‌‌​‌‌‌‌​​‌​​​‌‌‌‌​‌​​‌‌​‌​​​‌‌‌​​‌‌‌‌​‌‌‌​​‌​‌‌​​​‌‌​‌‌​‌‌​​​​‌‌‌​‌​​​‌​‌‌​​​‌‌​‌​​​​‌
> - 每个方案能直接进入阶段 0，不需要用户再补设定；
> - 每个方案标注风险与代价，供用户权衡；
> - 用户选定后，AI 加载对应扩展包组合，**冲突时以主题材为准**；
> - 主题材决定：世界底层规则、读者预期、爽点类型、语言基调；辅题材只做风味补充，不改变底层规则。
> - 禁止”两个题材各写一半”的拼贴式融合。
## 多题材融合处理​‌‍‌‌‌​‌​​​‌​‌‌​‌​‌‌​‌‌​​​​‌‌‌​‌​​​‌​‌‌​‌‌‌‌​​‌​​​‌‌‌‌​‌​​‌‌​‌​​​‌‌‌​​‌‌‌‌​‌‌‌​​‌​‌‌​​​‌‌​‌‌​‌‌​​​​‌‌‌​‌​​​‌​‌‌​​​‌‌​‌​​​​‌
### 触发条件​‌‍‌‌‌​‌​​​‌​‌‌​‌​‌‌​‌‌​​​​‌‌‌​‌​​​‌​‌‌​‌‌‌‌​​‌​​​‌‌‌‌​‌​​‌‌​‌​​​‌‌‌​​‌‌‌‌​‌‌‌​​‌​‌‌​​​‌‌​‌‌​‌‌​​​​‌‌‌​‌​​​‌​‌‌​​​‌‌​‌​​​​‌
用户提出 **3 个及以上题材混合**时触发，如「架空历史 + 军事 + 都市」「穿越 + 军事 + 架空历史 + 武侠」。

二元混合仍走「混合题材处理」，不走本节。

### 核心原则​‌‍‌‌‌​‌​​​‌​‌‌​‌​‌‌​‌‌​​​​‌‌‌​‌​​​‌​‌‌​‌‌‌‌​​‌​​​‌‌‌‌​‌​​‌‌​‌​​​‌‌‌​​‌‌‌‌​‌‌‌​​‌​‌‌​​​‌‌​‌‌​‌‌​​​​‌‌‌​‌​​​‌​‌‌​​​‌‌​‌​​​​‌
> **不搞平均主义，必须分主次、分层级。**
> 多题材融合不是把几个题材各写一半，而是各层各司其职。

### 题材分三层​‌‍‌‌‌​‌​​​‌​‌‌​‌​‌‌​‌‌​​​​‌‌‌​‌​​​‌​‌‌​‌‌‌‌​​‌​​​‌‌‌‌​‌​​‌‌​‌​​​‌‌‌​​‌‌‌‌​‌‌‌​​‌​‌‌​​​‌‌​‌‌​‌‌​​​​‌‌‌​‌​​​‌​‌‌​​​‌‌​‌​​​​‌
| 层 | 作用 | 数量限制 |
|----|------|---------|
| 世界观层 | 决定世界底层规则 | 1 主 + 0-2 辅 |
| 机制层 | 决定叙事驱动方式 | 0-1 个 |
| 风格层 | 决定叙事风格与氛围 | 0-2 个 |

### 第一层：世界观层​‌‍‌‌‌​‌​​​‌​‌‌​‌​‌‌​‌‌​​​​‌‌‌​‌​​​‌​‌‌​‌‌‌‌​​‌​​​‌‌‌‌​‌​​‌‌​‌​​​‌‌‌​​‌‌‌‌​‌‌‌​​‌​‌‌​​​‌‌​‌‌​‌‌​​​​‌‌‌​‌​​​‌​‌‌​​​‌‌​‌​​​​‌
决定世界底层规则。**同层互斥**，必须分主次。

| 题材 | 归属 |
|------|------|
| 历史 / 架空历史 | 世界观层 |
| 都市 | 世界观层 |
| 科幻 | 世界观层 |
| 仙侠 / 玄幻 | 世界观层 |
| 武侠 | 世界观层 |
| 奇幻 | 世界观层 |

**规则**：
- 世界观层固定「1 主 + 0-2 辅」。
- 同层互斥：架空历史与都市不能同时为主，必须分主次。
- 冲突时以主为准。

### 第二层：机制层​‌‍‌‌‌​‌​​​‌​‌‌​‌​‌‌​‌‌​​​​‌‌‌​‌​​​‌​‌‌​‌‌‌‌​​‌​​​‌‌‌‌​‌​​‌‌​‌​​​‌‌‌​​‌‌‌‌​‌‌‌​​‌​‌‌​​​‌‌​‌‌​‌‌​​​​‌‌‌​‌​​​‌​‌‌​​​‌‌​‌​​​​‌
决定叙事驱动方式。**不改变世界观底层规则**。

| 题材 | 归属 |
|------|------|
| 穿越 | 机制层 |
| 重生 | 机制层 |
| 快穿 | 机制层 |
| 穿书 | 机制层 |
| 无限流 / 系统流 | 机制层 |
| 游戏化 | 机制层 |

**规则**：
- 机制层固定「0-1 个」。
- 一个就够。多个机制互相干扰，不建议。
- 机制层不改变世界观硬设定，只做驱动。

### 第三层：风格层​‌‍‌‌‌​‌​​​‌​‌‌​‌​‌‌​‌‌​​​​‌‌‌​‌​​​‌​‌‌​‌‌‌‌​​‌​​​‌‌‌‌​‌​​‌‌​‌​​​‌‌‌​​‌‌‌‌​‌‌‌​​‌​‌‌​​​‌‌​‌‌​‌‌​​​​‌‌‌​‌​​​‌​‌‌​​​‌‌​‌​​​​‌
决定叙事风格与氛围。**只做风味补充**。

| 题材 | 归属 |
|------|------|
| 军事 | 风格层 |
| 悬疑 / 灵异 | 风格层 |
| 权谋 | 风格层 |
| 甜宠 / 虐恋 | 风格层 |
| 种田 / 日常 | 风格层 |

**规则**：
- 风格层固定「0-2 个」。
- 1 个风格最稳，基调统一鲜明。
- 2 个风格可制造张力，但需明确主次。
- 风格层不改变世界观和机制。

### 冲突处理优先级​‌‍‌‌‌​‌​​​‌​‌‌​‌​‌‌​‌‌​​​​‌‌‌​‌​​​‌​‌‌​‌‌‌‌​​‌​​​‌‌‌‌​‌​​‌‌​‌​​​‌‌‌​​‌‌‌‌​‌‌‌​​‌​‌‌​​​‌‌​‌‌​‌‌​​​​‌‌‌​‌​​​‌​‌‌​​​‌‌​‌​​​​‌
```
世界观层（主）> 世界观层（辅）> 机制层 > 风格层
```
- **世界观层冲突**：以主为准。架空历史 vs 都市冲突，以架空历史为准。
- **机制层 vs 世界观层**：机制层不改变世界观底层规则，只做驱动。
- **风格层 vs 前两层**：风格层只做风味补充，不改变世界观和机制。

### 处理流程​‌‍‌‌‌​‌​​​‌​‌‌​‌​‌‌​‌‌​​​​‌‌‌​‌​​​‌​‌‌​‌‌‌‌​​‌​​​‌‌‌‌​‌​​‌‌​‌​​​‌‌‌​​‌‌‌‌​‌‌‌​​‌​‌‌​​​‌‌​‌‌​‌‌​​​​‌‌‌​‌​​​‌​‌‌​​​‌‌​‌​​​​‌
1. **题材分层**：把用户说的题材按三层归类。
2. **确认各层的主次**：
   - 世界观层：1 主 + 0-2 辅。
   - 机制层：0-1 个。
   - 风格层：0-2 个。
3. **输出融合方案**（按复杂度给 3-5 个）。
4. 每个方案说明：
   - 世界观怎么融合；
   - 机制怎么嵌入；
   - 风格怎么叠加；
   - 冲突时谁让谁；
   - 风险与代价。
5. 用户选定后，加载对应扩展包组合。

### 方案模板（以「架空历史 + 军事 + 都市」为例）​‌‍‌‌‌​‌​​​‌​‌‌​‌​‌‌​‌‌​​​​‌‌‌​‌​​​‌​‌‌​‌‌‌‌​​‌​​​‌‌‌‌​‌​​‌‌​‌​​​‌‌‌​​‌‌‌‌​‌‌‌​​‌​‌‌​​​‌‌​‌‌​‌‌​​​​‌‌‌​‌​​​‌​‌‌​​​‌‌​‌​​​​‌
```

题材分层：
```

### 确认粒度​‌‍‌‌‌​‌​​​‌​‌‌​‌​‌‌​‌‌​​​​‌‌‌​‌​​​‌​‌‌​‌‌‌‌​​‌​​​‌‌‌‌​‌​​‌‌​‌​​​‌‌‌​​‌‌‌‌​‌‌‌​​‌​‌‌​​​‌‌​‌‌​‌‌​​​​‌‌‌​‌​​​‌​‌‌​​​‌‌​‌​​​​‌
分三步，避免信息过载：
1. 0b-1 大纲确认
2. 0b-2 人物小传确认

> **0b-2 附加确认（术语表 / 称谓表）**：确认人物小传时，同时确认本书的术语表与称谓表——关键术语（力量体系名、组织名、器物名）和人物称谓（谁叫谁什么、上下级/亲疏称谓）在此定死，写作中不换。定死后如需变更，走「已拍板修改」登记，不静默改。写作中不出现"发现不统一再统一"的改稿动作。

> **0b-2 附加确认（职业质感）**：确认人物小传后，判定主要角色里有没有「职业是角色核心身份」的（不是标签，是身份——如大厨、医生、律师、程序员、匠人；纯「公司职员」「学生」不算）。
> - 没有 → 跳过，`project/state-schema.md` 的 `profession_texture` 填「不启用」。
> - 有 → 问三件事：①哪些角色有职业特性（列名字 + 职业）；②是否需要在正文中详写职业工作流程（是 / 否 / 只在关键章写）；③若详写，频率（每 X 章至少一次）+ 深度（一笔带过 / 半场戏以内 / 完整流程，推荐半场戏以内，不超过一场戏的一半篇幅，防止水字数）。
> 确认后写入 `project/state-schema.md` 的 `profession_texture` 字段。此字段是细纲阶段「职业质感」标注的依据。

3. 0b-3 其余项（世界观、视角、篇幅、主题、风格、支线、爽点、黄金三章、流程）一次性确认

## 同类作品参考机制​‌‍‌‌‌​‌​​​‌​‌‌​‌​‌‌​‌‌​​​​‌‌‌​‌​​​‌​‌‌​‌‌‌‌​​‌​​​‌‌‌‌​‌​​‌‌​‌​​​‌‌‌​​‌‌‌‌​‌‌‌​​‌​‌‌​​​‌‌​‌‌​‌‌​​​​‌‌‌​‌​​​‌​‌‌​​​‌‌​‌​​​​‌
### 触发条件​‌‍‌‌‌​‌​​​‌​‌‌​‌​‌‌​‌‌​​​​‌‌‌​‌​​​‌​‌‌​‌‌‌‌​​‌​​​‌‌‌‌​‌​​‌‌​‌​​​‌‌‌​​‌‌‌‌​‌‌‌​​‌​‌‌​​​‌‌​‌‌​‌‌​​​​‌‌‌​‌​​​‌​‌‌​​​‌‌​‌​​​​‌

### 核心判断：区分「那种感觉」和「那本书」​‌‍‌‌‌​‌​​​‌​‌‌​‌​‌‌​‌‌​​​​‌‌‌​‌​​​‌​‌‌​‌‌‌‌​​‌​​​‌‌‌‌​‌​​‌‌​‌​​​‌‌‌​​‌‌‌‌​‌‌‌​​‌​‌‌​​​‌‌​‌‌​‌‌​​​​‌‌‌​‌​​​‌​‌‌​​​‌‌​‌​​​​‌

|---------|------|
| 那种感觉（类型、氛围、节奏、爽点） | 安全区，可做 |
| 那本书（情节、表达、人物、专有名词） | 禁区，拒绝 |
### 安全区（可做）​‌‍‌‌‌​‌​​​‌​‌‌​‌​‌‌​‌‌​​​​‌‌‌​‌​​​‌​‌‌​‌‌‌‌​​‌​​​‌‌‌‌​‌​​‌‌​‌​​​‌‌‌​​‌‌‌‌​‌‌‌​​‌​‌‌​​​‌‌​‌‌​‌‌​​​​‌‌‌​‌​​​‌​‌‌​​​‌‌​‌​​​​‌
1. 提取类型特征
2. 提取结构模式
3. 提取爽点类型
4. 提取读者期待
5. 作为题材锚点，转到题材机制
6. 作为风格锚点，转到 `style_anchor.md`
7. 作为避坑参考
> 共同点：提取的是**类型层面的共性**，不是**作品层面的专属**。
### 禁区（拒绝）​‌‍‌‌‌​‌​​​‌​‌‌​‌​‌‌​‌‌​​​​‌‌‌​‌​​​‌​‌‌​‌‌‌‌​​‌​​​‌‌‌‌​‌​​‌‌​‌​​​‌‌‌​​‌‌‌‌​‌‌‌​​‌​‌‌​​​‌‌​‌‌​‌‌​​​​‌‌‌​‌​​​‌​‌‌​​​‌‌​‌​​​​‌
1. 复制具体情节
2. 模仿具体表达、开篇句
3. 复制人物设定、专有名词体系
4. 写同人（**例外：原作进入公共领域时允许**）
5. 照搬「像 XXX 那样写」
6. 正文中出现那本书的专属名词
> 共同点：涉及**作品层面的专属**，一律拒绝。
> 依据：内容安全硬约束第 4 条。
### AI 不认识时的处理流程​‌‍‌‌‌​‌​​​‌​‌‌​‌​‌‌​‌‌​​​​‌‌‌​‌​​​‌​‌‌​‌‌‌‌​​‌​​​‌‌‌‌​‌​​‌‌​‌​​​‌‌‌​​‌‌‌‌​‌‌‌​​‌​‌‌​​​‌‌​‌‌​‌‌​​​​‌‌‌​‌​​​‌​‌‌​​​‌‌​‌​​​​‌
1. AI 不认识 → 明确说「我不确定这本书的具体内容」
2. 请用户提供：作者 / 书名 / 片段 / 链接
3. 用户提供 → 只用于识别类型特征，不用于仿写
4. 用户提供不了 → 转为类型特征询问：「你能描述一下你想要的那种感觉吗？比如题材、氛围、节奏、爽点类型。」
5. 从用户描述中提取关键词 → 匹配题材方向 → 加载对应扩展包
**禁止**：AI 不认识时假装知道、编造内容、凭空推荐「类似」。
### 用户提供原文片段的处理​‌‍‌‌‌​‌​​​‌​‌‌​‌​‌‌​‌‌​​​​‌‌‌​‌​​​‌​‌‌​‌‌‌‌​​‌​​​‌‌‌‌​‌​​‌‌​‌​​​‌‌‌​​‌‌‌‌​‌‌‌​​‌​‌‌​​​‌‌​‌‌​‌‌​​​​‌‌‌​‌​​​‌​‌‌​​​‌‌​‌​​​​‌
- 委婉拒绝直接仿写，给出理由：涉及版权与抄袭风险。
- 说明用途：片段只用于识别类型特征，不用于模仿具体表达。
- 给出替代方案：描述「那种感觉」，AI 从类型特征入手。
- 推荐写法：**提取共性，不复刻专属**。
### 同人请求的处理​‌‍‌‌‌​‌​​​‌​‌‌​‌​‌‌​‌‌​​​​‌‌‌​‌​​​‌​‌‌​‌‌‌‌​​‌​​​‌‌‌‌​‌​​‌‌​‌​​​‌‌‌​​‌‌‌‌​‌‌‌​​‌​‌‌​​​‌‌​‌‌​‌‌​​​​‌‌‌​‌​​​‌​‌‌​​​‌‌​‌​​​​‌
| 情况 | 处理 |
|------|------|
| 原作未进入公共领域 | 拒绝，说明版权风险 |
| 原作已进入公共领域 | 允许，但仍不得复制具体表达，只能作为题材/风格参考 |
| 用户有授权 | 用户需自行说明授权情况，AI 仍不模仿具体表达 |
### 与现有机制挂接​‌‍‌‌‌​‌​​​‌​‌‌​‌​‌‌​‌‌​​​​‌‌‌​‌​​​‌​‌‌​‌‌‌‌​​‌​​​‌‌‌‌​‌​​‌‌​‌​​​‌‌‌​​‌‌‌‌​‌‌‌​​‌​‌‌​​​‌‌​‌‌​‌‌​​​​‌‌‌​‌​​​‌​‌‌​​​‌‌​‌​​​​‌
