## 系列架构层​‌‍‌‌‌​‌​​​‌​‌‌​‌​‌‌​‌‌​​​​‌‌‌​‌​​​‌​‌‌​‌‌‌‌​​‌​​​‌‌‌‌​‌​​‌‌​‌​​​‌‌‌​​‌‌‌‌​‌‌‌​​‌​‌‌​​​‌‌​‌‌​‌‌​​​​‌‌‌​‌​​​‌​‌‌​​​‌‌​‌​​​​‌
仅**系列作品**加载。单部、短篇不加载。

### 6 个组件​‌‍‌‌‌​‌​​​‌​‌‌​‌​‌‌​‌‌​​​​‌‌‌​‌​​​‌​‌‌​‌‌‌‌​​‌​​​‌‌‌‌​‌​​‌‌​‌​​​‌‌‌​​‌‌‌‌​‌‌‌​​‌​‌‌​​​‌‌​‌‌​‌‌​​​​‌‌‌​‌​​​‌​‌‌​​​‌‌​‌​​​​‌
| 组件 | 作用 | 落点 |
|------|------|------|
| 系列总纲 | 部数、各部定位、主线总走向、大结局基调 | `series_outline.md` |
| 系列状态库 | 跨部传递：核心人物状态、核心伏笔、世界状态 | `series_state.md` |
| 跨部伏笔表 | 埋设部/章、计划回收部/章、实际回收部/章、状态 | `series_foreshadowing.md` |
| 跨部人物弧光表 | 主角弧光跨多部的阶段设计 | `series_arc.md` |
| 部间接口协议 | 部结报告模板 + 部初始化模板 + 部级摘要 B1、B2…… | `series_interface.md` |
| 文风锚点基线 | 多部共用，每部开头校准 | `series_style_anchor.md` |

用户选「建立系列架构层」后，在阶段 0b 额外确认：

```
• 主线总走向：……
• 大结局基调：……
二、系列状态库（跨部传递）
• 核心人物状态：……
• 核心伏笔：……
• 世界状态：……
三、部间接口协议
• 部结报告模板：……
• 部初始化模板：……
• 跨部伏笔登记规则：……
• 文风校准规则：……
```

### 部内 vs 部间​‌‍‌‌‌​‌​​​‌​‌‌​‌​‌‌​‌‌​​​​‌‌‌​‌​​​‌​‌‌​‌‌‌‌​​‌​​​‌‌‌‌​‌​​‌‌​‌​​​‌‌‌​​‌‌‌‌​‌‌‌​​‌​‌‌​​​‌‌​‌‌​‌‌​​​​‌‌‌​‌​​​‌​‌‌​​​‌‌​‌​​​​‌
| 项 | 部内 | 部间 |
|----|------|------|
| 摘要树 | S1 从本部第 1 章重新编号 | 部级摘要 B1、B2…… |
| 状态库 | 本部状态库独立 | 系列状态库跨部持久化 |
| 伏笔表 | 本部伏笔表，标「跨部」的指向系列状态库 | 跨部伏笔表单独登记 |
| 文风 | 部内统一 | 每部开头对照文风锚点基线校准 |

### 系列级验收（第 1 部完成后专属）​‌‍‌‌‌​‌​​​‌​‌‌​‌​‌‌​‌‌​​​​‌‌‌​‌​​​‌​‌‌​‌‌‌‌​​‌​​​‌‌‌‌​‌​​‌‌​‌​​​‌‌‌​​‌‌‌‌​‌‌‌​​‌​‌‌​​​‌‌​‌‌​‌‌​​​​‌‌‌​‌​​​‌​‌‌​​​‌‌​‌​​​​‌
第 1 部完成后，除部结报告外，**额外执行一次系列级验收**，再决定是否继续第 2 部。

#### 触发时机​‌‍‌‌‌​‌​​​‌​‌‌​‌​‌‌​‌‌​​​​‌‌‌​‌​​​‌​‌‌​‌‌‌‌​​‌​​​‌‌‌‌​‌​​‌‌​‌​​​‌‌‌​​‌‌‌‌​‌‌‌​​‌​‌‌​​​‌‌​‌‌​‌‌​​​​‌‌‌​‌​​​‌​‌‌​​​‌‌​‌​​​​‌
第 1 部结尾、部结报告输出之后，进入第 2 部之前。

#### 与部结报告的区别​‌‍‌‌‌​‌​​​‌​‌‌​‌​‌‌​‌‌​​​​‌‌‌​‌​​​‌​‌‌​‌‌‌‌​​‌​​​‌‌‌‌​‌​​‌‌​‌​​​‌‌‌​​‌‌‌‌​‌‌‌​​‌​‌‌​​​‌‌​‌‌​‌‌​​​​‌‌‌​‌​​​‌​‌‌​​​‌‌​‌​​​​‌
| 概念 | 频率 | 作用 |
|------|------|------|
| 部结报告 | 每部结尾都做 | 部间交接文件，记录本部定格状态 |
| 系列级验收 | **仅第 1 部完成后** | 系列可行性验收，决定要不要继续做下去 |

#### 验收内容（4 项）​‌‍‌‌‌​‌​​​‌​‌‌​‌​‌‌​‌‌​​​​‌‌‌​‌​​​‌​‌‌​‌‌‌‌​​‌​​​‌‌‌‌​‌​​‌‌​‌​​​‌‌‌​​‌‌‌‌​‌‌‌​​‌​‌‌​​​‌‌​‌‌​‌‌​​​​‌‌‌​‌​​​‌​‌‌​​​‌‌​‌​​​​‌
1. **系列总纲可行性**：主线总走向是否成立，大结局基调是否还合适，各部定位是否清晰。
2. **跨部伏笔合理性**：第 1 部埋的跨部伏笔，是否还能按原计划在第 2-5 部回收；有没有写崩的。
3. **人物弧光连贯性**：主角弧光跨多部的阶段设计，第 1 部走完后的实际状态，是否和系列弧光表一致。
4. **文风与节奏基线**：第 1 部的实际文风，是否和 `series_style_anchor.md` 基线一致；节奏是否符合系列规划。

#### 输出格式​‌‍‌‌‌​‌​​​‌​‌‌​‌​‌‌​‌‌​​​​‌‌‌​‌​​​‌​‌‌​‌‌‌‌​​‌​​​‌‌‌‌​‌​​‌‌​‌​​​‌‌‌​​‌‌‌‌​‌‌‌​​‌​‌‌​​​‌‌​‌‌​‌‌​​​​‌‌‌​‌​​​‌​‌‌​​​‌‌​‌​​​​‌
```
【系列级验收报告 · 第 1 部完成后】
一、系列总纲可行性：通过 / 需调整
• 问题：……
• 建议：……
二、跨部伏笔合理性：通过 / 需调整
• 第 1 部已埋跨部伏笔：……
• 可回收性评估：……
三、人物弧光连贯性：通过 / 需调整
• 主角第 1 部实际弧光：……
• 与系列弧光表对照：……
四、文风与节奏基线：通过 / 需调整
• 实际文风与基线差异：……
五、结论：可继续第 2 部 / 需先调整系列总纲 / 建议重新评估系列规划
```

#### 处理规则​‌‍‌‌‌​‌​​​‌​‌‌​‌​‌‌​‌‌​​​​‌‌‌​‌​​​‌​‌‌​‌‌‌‌​​‌​​​‌‌‌‌​‌​​‌‌​‌​​​‌‌‌​​‌‌‌‌​‌‌‌​​‌​‌‌​​​‌‌​‌‌​‌‌​​​​‌‌‌​‌​​​‌​‌‌​​​‌‌​‌​​​​‌
- 验收通过：进入第 2 部，执行部初始化。
- 验收不通过：先调整系列总纲 / 跨部伏笔表 / 人物弧光表，用户确认后再进入第 2 部。
- 验收发现系列规划不可行：允许用户调整部数、调整结局基调，或改为单部收尾。
### 部结报告（每部结尾输出）​‌‍‌‌‌​‌​​​‌​‌‌​‌​‌‌​‌‌​​​​‌‌‌​‌​​​‌​‌‌​‌‌‌‌​​‌​​​‌‌‌‌​‌​​‌‌​‌​​​‌‌‌​​‌‌‌‌​‌‌‌​​‌​‌‌​​​‌‌​‌‌​‌‌​​​​‌‌‌​‌​​​‌​‌‌​​​‌‌​‌​​​​‌
```
【部结报告 · 第X部】
• 本部字数：……
• 本部章节：第 X-Y 章
• 已回收伏笔：……
• 跨部伏笔（留到下一部）：……
• 人物状态定格：主角/关键配角/反派
• 世界状态定格：……
• 本部遗留问题：……
• 下一部建议起点：……
```

### 部初始化（每部开头执行）​‌‍‌‌‌​‌​​​‌​‌‌​‌​‌‌​‌‌​​​​‌‌‌​‌​​​‌​‌‌​‌‌‌‌​​‌​​​‌‌‌‌​‌​​‌‌​‌​​​‌‌‌​​‌‌‌‌​‌‌‌​​‌​‌‌​​​‌‌​‌‌​‌‌​​​​‌‌‌​‌​​​‌​‌‌​​​‌‌​‌​​​​‌
```
1. 读系列状态库 + 上一部部结报告
2. 加载系列总纲中本部定位
3. 确认本部大纲、人物小传、篇幅
4. 初始化本部状态库（继承系列状态库 + 本部新增）
5. 初始化本部滚动摘要树（S1 从本部第 1 章算起）
6. 文风校准（对照系列文风锚点基线）
7. 用户确认后，进入本部阶段 1
```

### 跨部伏笔表​‌‍‌‌‌​‌​​​‌​‌‌​‌​‌‌​‌‌​​​​‌‌‌​‌​​​‌​‌‌​‌‌‌‌​​‌​​​‌‌‌‌​‌​​‌‌​‌​​​‌‌‌​​‌‌‌‌​‌‌‌​​‌​‌‌​​​‌‌​‌‌​‌‌​​​​‌‌‌​‌​​​‌​‌‌​​​‌‌​‌​​​​‌
```
【跨部伏笔表 · 系列状态库】

| 伏笔 | 埋设部/章 | 计划回收部/章 | 实际回收部/章 | 状态 | 备注 |
|------|----------|--------------|--------------|------|------|
| 玉佩刻纹 | 第1部/第3章 | 第4部/第20章 | — | 待回收 | 跨部 |
```

本部伏笔表只记本部内伏笔，跨部伏笔在本部伏笔表里标「跨部，详见系列状态库」。

### 部级摘要​‌‍‌‌‌​‌​​​‌​‌‌​‌​‌‌​‌‌​​​​‌‌‌​‌​​​‌​‌‌​‌‌‌‌​​‌​​​‌‌‌‌​‌​​‌‌​‌​​​‌‌‌​​‌‌‌‌​‌‌‌​​‌​‌‌​​​‌‌​‌‌​‌‌​​​​‌‌‌​‌​​​‌​‌‌​​​‌‌​‌​​​​‌
每部结尾生成一段「部级摘要」，编号 B1、B2……，追加到 `series_interface.md`。
- 格式：`[第X部] 核心事件；人物变化；跨部伏笔状态；主线进度。`
- 跨部携带时，带的是「部级摘要 + 系列状态库」，不是上一部的全部 S 摘要。

### 文风跨部校准​‌‍‌‌‌​‌​​​‌​‌‌​‌​‌‌​‌‌​​​​‌‌‌​‌​​​‌​‌‌​‌‌‌‌​​‌​​​‌‌‌‌​‌​​‌‌​‌​​​‌‌‌​​‌‌‌‌​‌‌‌​​‌​‌‌​​​‌‌​‌‌​‌‌​​​​‌‌‌​‌​​​‌​‌‌​​​‌‌​‌​​​​‌
每部开头执行，对比前期样本和当前文本，发现漂移就校正。文风锚点基线存于 `series_style_anchor.md`。
## 多作品并行处理规则​‌‍‌‌‌​‌​​​‌​‌‌​‌​‌‌​‌‌​​​​‌‌‌​‌​​​‌​‌‌​‌‌‌‌​​‌​​​‌‌‌‌​‌​​‌‌​‌​​​‌‌‌​​‌‌‌‌​‌‌‌​​‌​‌‌​​​‌‌​‌‌​‌‌​​​​‌‌‌​‌​​​‌​‌‌​​​‌‌​‌​​​​‌
### 触发条件​‌‍‌‌‌​‌​​​‌​‌‌​‌​‌‌​‌‌​​​​‌‌‌​‌​​​‌​‌‌​‌‌‌‌​​‌​​​‌‌‌‌​‌​​‌‌​‌​​​‌‌‌​​‌‌‌‌​‌‌‌​​‌​‌‌​​​‌‌​‌‌​‌‌​​​​‌‌‌​‌​​​‌​‌‌​​​‌‌​‌​​​​‌
用户要求同时做多部作品，或一次开多个题材，如「给我出五部 20 万字的小说，题材各不相同」。
### 与系列架构层的区别​‌‍‌‌‌​‌​​​‌​‌‌​‌​‌‌​‌‌​​​​‌‌‌​‌​​​‌​‌‌​‌‌‌‌​​‌​​​‌‌‌‌​‌​​‌‌​‌​​​‌‌‌​​‌‌‌‌​‌‌‌​​‌​‌‌​​​‌‌​‌‌​‌‌​​​​‌‌‌​‌​​​‌​‌‌​​​‌‌​‌​​​​‌
| 概念 | 说明 |
|------|------|
| 系列作品 | 同一世界观、同一主线、多部串行，共享系列状态库 |
| 多作品并行 | 不同世界观、不同题材、互不相关，各自独立 |
**这两个不能混。** 用户说「五部题材各不相同」，属于多作品并行，不是系列。
### 核心规则​‌‍‌‌‌​‌​​​‌​‌‌​‌​‌‌​‌‌​​​​‌‌‌​‌​​​‌​‌‌​‌‌‌‌​​‌​​​‌‌‌‌​‌​​‌‌​‌​​​‌‌‌​​‌‌‌‌​‌‌‌​​‌​‌‌​​​‌‌​‌‌​‌‌​​​​‌‌‌​‌​​​‌​‌‌​​​‌‌​‌​​​​‌
1. 每部作品独立目录，独立状态库、摘要树、扩展包。
2. 禁止共用一个状态库或摘要树。
3. 每部独立编号（部内 S1 从本部第 1 章算）。
4. **当前活跃作品只能有一个**，切换需用户明确指令。
5. 非活跃作品的状态库、摘要冻结，不主动携带。
6. 每部仍独立走规模确认 + 题材确认 + 阶段 0。
### 处理流程​‌‍‌‌‌​‌​​​‌​‌‌​‌​‌‌​‌‌​​​​‌‌‌​‌​​​‌​‌‌​‌‌‌‌​​‌​​​‌‌‌‌​‌​​‌‌​‌​​​‌‌‌​​‌‌‌‌​‌‌‌​​‌​‌‌​​​‌‌​‌‌​‌‌​​​​‌‌‌​‌​​​‌​‌‌​​​‌‌​‌​​​​‌
1. 确认部数、题材、每部规模。
2. 确认串行还是并行。
3. 串行：做完一部再开下一部。
4. 并行：每部独立目录，切换时明确「当前作品：第X部」。
5. 每部开头执行部初始化。
### 默认推荐​‌‍‌‌‌​‌​​​‌​‌‌​‌​‌‌​‌‌​​​​‌‌‌​‌​​​‌​‌‌​‌‌‌‌​​‌​​​‌‌‌‌​‌​​‌‌​‌​​​‌‌‌​​‌‌‌‌​‌‌‌​​‌​‌‌​​​‌‌​‌‌​‌‌​​​​‌‌‌​‌​​​‌​‌‌​​​‌‌​‌​​​​‌
- **串行**：先做完第 1 部，验收后再开第 2 部。最稳。
- **先做一部试跑**：先做第 1 部的前几章，验证机制，再决定要不要开其余。
- 并行是最后选项，需用户明确坚持。
### 并行问题提示（必读）​‌‍‌‌‌​‌​​​‌​‌‌​‌​‌‌​‌‌​​​​‌‌‌​‌​​​‌​‌‌​‌‌‌‌​​‌​​​‌‌‌‌​‌​​‌‌​‌​​​‌‌‌​​‌‌‌‌​‌‌‌​​‌​‌‌​​​‌‌​‌‌​‌‌​​​​‌‌‌​‌​​​‌​‌‌​​​‌‌​‌​​​​‌
用户选择并行时，AI **必须**提示以下问题，让用户知情后再决定：
```
【并行风险提示】
并行做多部作品，会带来以下问题：
1. 状态库隔离风险：五部各自一套人物、时间线、伏笔，一旦混用，全线污染。
2. 题材串味风险：五部加载不同扩展包，切换时容易把 A 题材的意象带进 B 题材。
3. 文风漂移风险：多部交替写，文风锚点容易互相干扰，越写越不像。
4. 上下文压力：每轮只能带一部，切换时需重新加载，效率低。
5. 进度管理复杂：五部进度面板各自独立，用户容易跟丢。
6. 一致性成本：每部都要维护独立状态库、摘要树，管理成本 ×5。
7. 质量风险：交替写容易顾此失彼，单部质量可能不如串行。
建议：优先串行，或先做一部试跑。若坚持并行，AI 会严格隔离，但上述风险由用户承担。
```
### 并行时的硬约束​‌‍‌‌‌​‌​​​‌​‌‌​‌​‌‌​‌‌​​​​‌‌‌​‌​​​‌​‌‌​‌‌‌‌​​‌​​​‌‌‌‌​‌​​‌‌​‌​​​‌‌‌​​‌‌‌‌​‌‌‌​​‌​‌‌​​​‌‌​‌‌​‌‌​​​​‌‌‌​‌​​​‌​‌‌​​​‌‌​‌​​​​‌
若用户坚持并行，AI 必须：
1. 每部独立任务目录。
2. 每部独立状态库文件（`characters.md` 等加部前缀，如 `book1_characters.md`）。
3. 每部独立摘要树。
4. 每轮开始前明确「当前作品：第X部」。
5. 不跨部引用人物、伏笔、摘要。
6. 切换作品时，重新加载该部状态库，不携带其他部的内容。
